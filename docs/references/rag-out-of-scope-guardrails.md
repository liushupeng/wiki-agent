# RAG 越界防线：对 wiki-agent 的借鉴

## 来源

- 本地原文：[基于大模型的 RAG 系统解决用户提问不在知识库范围内的问题](../../../blog/基于大模型的RAG系统解决用户提问不在知识库范围内的问题.md)
- 扩展分析：[rag-out-of-scope-review.md](../../../blog-analysis/rag-out-of-scope-review.md)
- 阅读日期：2026-07-22

原文讨论“检索系统在知识库没有答案时仍生成看似合理的回答”的风险。它提出意图边界、检索充分性、受约束生成、输出校验与离线知识治理的多层防线。

## 核心观点

| 防线 | 目标 | 对 wiki-agent 的适配原则 |
|---|---|---|
| 知识库边界 | 让明显不相关的问题不进入完整检索链路 | 用简短、可维护的覆盖范围说明辅助判断；不以边界规则替代检索。 |
| 检索充分性 | 区分“Top K 相对最相似”与“证据实际足以回答” | 不直接以当前 TF 向量分数设置全局拒答阈值。 |
| 分级回答 | 区分完整命中、部分命中和无关结果 | 对部分证据明确说明边界；对无证据问题不根据弱相关片段补全。 |
| 生成约束 | 要求答案基于证据并提供来源 | 保留 Wiki/raw 来源与引用，限制无来源的事实性扩写。 |
| 高风险输出校验 | 在敏感领域检查事实是否可由证据支持 | 仅在风险或不确定性足够高时按需启用，避免默认增加多次 LLM 调用。 |
| 离线治理闭环 | 高频拒答和纠正应推动资料补全或检索改进 | trace、bad case、eval 和 Wiki 维护应连成闭环。 |

## 当前基础与缺口

| 维度 | 当前状态 | 相关位置 |
|---|---|---|
| 多源、可追溯检索 | 已具备 | `config/knowledge.sources.jsonc`、`src/rag/sourceRoots.ts` |
| Wiki-first 排序 | 已具备 | `src/rag/ranking.ts`、`src/rag/evaluation.ts` |
| 分阶段检索工具 | 已具备 | `src/tools/ragTool.ts` |
| 证据来源与执行 trace | 已具备 | `src/trace/`、`src/tools/ragTool.ts` |
| 检索充分性判定 | 未显式实现 | 当前 Top K 不等于可回答 |
| 知识库边界说明 | 未形成统一的 Agent 可读策略 | 目录结构本身不足以表达覆盖范围 |
| 分级拒答协议 | 未形成端到端行为契约 | 需要定义 `SUFFICIENT`、`PARTIAL`、`IRRELEVANT` 的回答边界 |
| 高频越界问题治理 | 有 bad case 与评测基础，但尚未固化流程 | `evaluation/badcases/`、`scripts/rag/` |

## 采纳路径

### P0：先观测，不先设阈值

为真实问题记录并审查：

- Top K 的相对分数、来源分布和实际读取的 chunk；
- 最终回答引用了哪些证据；
- 用户纠正、拒答与低质量回答；
- 同一问题在不同检索策略下的结果。

固定相似度阈值不应作为当前拒答条件：它会随 query、资料分布和 `TfEmbedder` 的词项特征变化而失真。

### P1：定义知识库边界与分级回答契约

补充面向 Agent 的边界说明：已覆盖主题、明确未覆盖主题、易混淆边界和推荐引导方式。

定义三种结果：

| 状态 | 行为 |
|---|---|
| `SUFFICIENT` | 只基于证据回答，并列出关键来源。 |
| `PARTIAL` | 回答证据覆盖的部分，明确未覆盖或无法确认的部分。 |
| `IRRELEVANT` | 明确当前资料未覆盖；可提供相近主题或建议用户补充描述。 |

该协议应成为系统提示、端到端评测和 bad case 的共同契约，而不只是文案约定。

### P2：按风险引入充分性裁判

对低相关但无法由确定性规则判断的请求，额外评估“问题 + 候选证据”是否足以回答，并输出上述三态。

该步骤会增加模型调用、成本和延迟，因此仅适用于：

- 用户明确要求严格依据知识库；
- 需要高可信结论的主题；
- 证据疑似相关但覆盖范围不明确的请求。

### P3：形成知识治理闭环

```text
IRRELEVANT / PARTIAL / 用户纠正
→ bad case 与 trace
→ 判断资料缺失、检索失败或明确越界
→ 补 raw / 更新 Wiki / 调整检索或边界
→ 加入评测并回归验证
```

长期目标是提升知识覆盖与证据质量，而不是持续叠加拒答逻辑。

## 不直接采纳

- **默认双 LLM 校验**：生成前裁判和生成后事实校验会显著提高成本与延迟，个人知识库不应默认开启。
- **单一全局相似度阈值**：在缺乏标注样本前，无法可靠判定跨主题、跨表述的问题。
- **只靠“回答不知道”的 prompt**：它不能区分弱相关证据、部分证据和真实无关结果，也没有离线治理闭环。

## 对当前项目的结论

该资料最有价值的结论是：拒答不是单一提示词功能，而是检索、回答和知识治理共享的质量协议。wiki-agent 应先利用已有 trace、bad case 与 RAG eval 收集真实样本，再将分级回答和边界说明做成可测试的行为契约。
