# LLM Wiki：对 wiki-agent 的借鉴

## 来源

- 本地资料：[karpathy：llm-wiki.md](../../../blog/karpathy：llm-wiki.md)
- 阅读日期：2026-07-22
- 原始链接：本地文本未保留可定位的原文 URL。

该材料提出一种个人知识库模式：将不可变的原始资料、由 LLM 持续维护的 Wiki，以及约束维护流程的 schema 分层。它与 wiki-agent 的定位高度相关，但其具体目录、工具和 Obsidian 工作流都只是可选实现。

## 核心观点

| 观点 | 含义 | 对 wiki-agent 的启发 |
|---|---|---|
| Wiki 是持续累积的知识产物 | 不要让模型在每次提问时都从 raw 文档重新拼接结论 | 将高价值的跨文档结论沉淀到 `wiki/`，并在检索时优先使用。 |
| 原始资料不可变 | raw 层是可回溯证据，不应被 Agent 改写 | 保持 `raw/` 只读，将整理、摘要与观点写入 `wiki/`。 |
| schema 决定维护质量 | 目录规范、页面格式、引用规则和操作流程将通用模型约束为 Wiki 维护者 | 用 `wiki/AGENTS.md` 维护 Wiki 结构、引用与更新约定。 |
| Ingest 是知识整合而非单纯索引 | 新资料应触发摘要、交叉引用、主题页更新和冲突标记 | 知识接入需要区分“建立检索索引”与“维护 Wiki”，后者应由明确流程和人工复核驱动。 |
| Query 的结果可以回写 | 高价值的分析、比较和新连接不应只停留在聊天记录 | 对可复用的问答结论，允许在确认后沉淀为 Wiki 页面。 |
| Index 与 log 分工 | 内容索引帮助定位；时间日志解释知识库怎样演化 | 维护可导航的 Wiki 索引，并为 ingest、关键更新和 lint 保留可审计记录。 |
| Lint 使知识库保持健康 | 定期发现孤儿页面、冲突、过时结论、缺失引用和知识空洞 | 将 Wiki 健康检查视为维护任务，不等同于向量索引是否构建成功。 |

## 已落地的映射

| 设计 | 对应实现 | 说明 |
|---|---|---|
| raw / wiki 双层知识源 | `config/knowledge.sources.jsonc`、`src/rag/sourceRoots.ts` | 原始资料与维护型 Wiki 分开配置，并保留来源前缀。 |
| Wiki-first 检索 | `src/rag/ranking.ts`、`src/tools/ragTool.ts` | 优先返回 Wiki 结果，raw 作为证据补充与可追溯来源。 |
| Schema 驱动的 Wiki 维护 | `wiki/AGENTS.md` | 为 Agent 定义 Wiki 的结构与维护规则。 |
| 可组合的检索与局部阅读 | `search_notes`、`grep_notes`、`read_note`、`related_notes` | 让 Agent 先定位、再阅读和扩展关联，而不是将整库内容送入上下文。 |
| 原始资料索引 | `scripts/rag/indexKnowledgeBase.ts`、`src/rag/indexPipeline.ts` | 索引阶段只进行本地切分和嵌入，不调用 LLM 修改来源文件。 |
| 可观测的维护与问答过程 | `src/trace/`、`var/traces/` | 能追踪检索、阅读、工具执行和模型调用，为后续改进提供依据。 |

## 近期候选

### 1. 定义 Wiki 的显式生命周期

将以下操作区分为独立、可审查的工作流：

```text
ingest：raw source → 摘要 / 来源页 / 主题页更新
query：检索 Wiki 与 raw → 证据化回答
promote：有价值的回答 → 用户确认 → 新增或更新 Wiki 页面
lint：检查链接、引用、冲突、孤儿页面、过时结论与知识空洞
```

当前索引构建解决的是 `raw/wiki → 可检索索引`，不应与 ingest 或 Wiki 写入混为一谈。

### 2. 增加内容索引与演化日志

当 `wiki/` 规模足够大、目录结构无法直接导航时，评估增加：

- `wiki/index.md`：按主题列出页面、简短说明、关键来源与更新时间；
- `wiki/log.md`：追加记录 ingest、页面升级、冲突处理和 lint 结论。

这两个文件应由明确的 Wiki 维护流程更新；不要将每一次普通问答都写入日志。

### 3. 将 Wiki lint 作为离线维护任务

首先实现低成本、确定性的检查，例如：

- Markdown 链接是否失效；
- 页面是否缺少来源或引用；
- 是否存在未被引用的孤儿页；
- index 是否遗漏页面。

语义冲突、重复主题和知识空洞可先输出候选清单供人工判断，不应让模型无监督地改写结论。

## 暂不采纳

| 做法 | 原因 |
|---|---|
| 以 `index.md` 替代检索索引 | 资料规模增长后，目录索引无法代替现有的语义、关键词和局部阅读工具。 |
| 自动将每个回答回写 Wiki | 聊天结论可能不完整、缺乏证据或不符合页面边界；必须经过来源校验与用户确认。 |
| 批量无监督 ingest | 单次触及多个页面容易放大错误和冲突；现阶段优先采用小批量、可审查的维护。 |
| 直接采用 Obsidian、qmd 或 MCP | 它们是界面/工具选择，不是该模式的必要条件；应由实际检索性能与使用方式决定。 |

## 对当前项目的结论

wiki-agent 已具备该模式最关键的基础：raw 与 wiki 分层、Wiki-first 检索、schema 约束和本地索引。下一步不应重复建设另一个 RAG，而是把“Wiki 如何被可靠地增量维护”明确成可审查的 ingest、promote 与 lint 工作流。
